# Server & Client Modes

Claude-Mem can be split across machines: one **server** holds all memory in Postgres,
and any number of thin **clients** send their observations to it and recall context
from it. This is built for a personal multi-device setup — your laptop, desktop, and
the server box itself all share one memory pool over a trusted network (e.g. Tailscale).

<Note>
These modes require the **server-beta** runtime (Postgres + Valkey + Docker), not the
default local SQLite worker. Generation runs on the server, so **clients never need a
provider API key.**
</Note>

<Note>
**Installing the CLI.** The commands below use this fork's package
`@bjlee2024/claude-mem`. Before it's published to npm, run the same commands
straight from GitHub — replace `npx @bjlee2024/claude-mem` with
`npx github:bjlee2024/claude-mem`. Server-side commands that touch the database
(`server enroll`, `install --mode server`) currently require **Bun**; run those on
the server host from a local clone: `bun dist/npx-cli/index.js …`.
</Note>

## When to use it

| You want… | Use |
| --- | --- |
| Memory on one machine only | Default install (local worker) |
| One backend, several devices sharing memory | **Server** on one box, **client** on each device |
| The server box to also capture its own Claude Code work | Server with `--with-local-client` (default) |

## How it works

```
[laptop]   claude-mem (client) ─┐
[desktop]  claude-mem (client) ─┼─ Tailscale/HTTP → [server] claude-mem (server)
[server]   (local client)      ─┘                     Postgres + Valkey + worker (generation)
```

- **Writes** — each hook posts the tool use to the server's `/v1/events`. If the
  server is unreachable, the event is queued to a local **spool**
  (`~/.claude-mem/spool/pending.ndjson`) and re-sent on the next hook. No memory is lost
  while the server is down.
- **Reads** — at session start the client pulls recent memory from the server's
  `/v1/context` and injects it. Offline, context injection is simply skipped (never
  blocks your session).
- **Per-repo isolation** — the client maps each repository to its own server project by
  name (the same isolation local mode gives you), so memory from one repo doesn't bleed
  into another. The mapping is cached in `~/.claude-mem/project-map.json`.
- **Generation** — the client sends raw events; the server's worker compresses and
  summarizes them. The client has no model, no SQLite, no Chroma.

## 1. Set up the server

On the machine that will hold memory:

```bash
npx @bjlee2024/claude-mem install --mode server
```

This brings up the server-beta Docker stack (Postgres, Valkey, server, worker), applies
the schema, and configures this box as a local client too. To run a pure backend with no
local capture, pass `--no-local-client`.

<Note>
The stack's compose file requires Postgres credentials and the server-beta env vars. See
the [Beta Features](/beta-features) and deployment notes for the `docker-compose` setup,
and keep the server reachable only over a trusted network.
</Note>

### Keep it always-on (systemd)

Register the stack as a service so it survives reboots:

```ini
# /etc/systemd/system/claude-mem.service
[Unit]
Description=claude-mem server-beta stack
Requires=docker.service
After=docker.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/path/to/claude-mem
ExecStart=/usr/bin/docker compose -p claude-mem -f docker-compose.my.yml up -d --remove-orphans
ExecStop=/usr/bin/docker compose -p claude-mem -f docker-compose.my.yml stop

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable docker.service
sudo systemctl enable --now claude-mem.service
```

## 2. Enroll a device

Generate a one-line enrollment token on the server. **Use the address your other devices
can actually reach** — a tailnet IP, not `localhost`:

```bash
npx @bjlee2024/claude-mem server enroll --url http://100.x.y.z:37700 --label laptop
```

It prints:

```
Enroll a device with:
  npx @bjlee2024/claude-mem install --mode client --enroll eyJ1cmwiOiJodHRw...
```

The token bundles the server URL and a **team-scoped API key** (read + write, no fixed
project — the client resolves projects per repo). Treat it like a password: it's printed
once, paste it over a trusted channel.

<Note>
`server enroll` is part of the host CLI and needs database access. Run it where
`CLAUDE_MEM_SERVER_DATABASE_URL` points at the server's Postgres (typically on the server
host). If Postgres isn't published to the host, target the container's address.
</Note>

### Where the token comes from (and what if you lose it)

The token is **printed once, at enroll time** — there is nowhere to look it up
later. The server stores only a hash of the underlying API key, never the raw
token. If you lose it, just run `server enroll` again to mint a new one; existing
devices are unaffected (each device gets its own key). Treat the token like a
password — it embeds a read+write API key — so don't paste it into chats or logs.

Use a distinct `--label` per device so you can revoke one device later without
touching the others:

```bash
npx @bjlee2024/claude-mem server api-key revoke   # revoke a specific device's key
```

When the server runs in the Docker stack (Postgres not published to the host),
point the CLI at the Postgres container's address:

```bash
PG_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' claude-mem-postgres-1)
CLAUDE_MEM_SERVER_DATABASE_URL="postgres://<user>:<pass>@$PG_IP:5432/<db>" \
  npx @bjlee2024/claude-mem server enroll --url http://<server-reachable-host>:37700 --label my-laptop
```

## 3. Install the client

On each device:

```bash
npx @bjlee2024/claude-mem install --mode client --enroll <token>
```

Or without a token:

```bash
npx @bjlee2024/claude-mem install --mode client --server-url http://100.x.y.z:37700 --token <api-key>
```

The client install:

- Writes `CLAUDE_MEM_RUNTIME=client` plus the server URL and key (to `~/.claude-mem`, mode `0600`).
- Installs the IDE hooks.
- **Skips** the local worker, SQLite, Chroma, and the provider-key prompt.
- Runs a best-effort reachability check (a warning, not a failure — you can install an
  offline laptop and it will sync later).

That's it — open Claude Code and work normally. Observations flow to the server; past
memory is injected at session start.

## 4. Verify

```bash
npx @bjlee2024/claude-mem client status
```

```json
{
  "runtime": "client",
  "server": "http://100.x.y.z:37700",
  "reachable": true,
  "spoolDepth": 0
}
```

- `reachable: true` — the server answered `/v1/info`.
- `spoolDepth` — how many writes are queued offline (0 means everything is synced).

## Offline behavior

If the server is down or the network drops:

1. Your Claude Code session is **never blocked** — hooks fail silently into the spool.
2. Observations accumulate in `~/.claude-mem/spool/pending.ndjson` (`client status` shows
   a rising `spoolDepth`).
3. When the server comes back, the next hook **flushes the spool** and re-sends everything.
   Replays are idempotent — duplicate sends are de-duplicated server-side, so nothing is
   doubled.

Context injection (recall) is skipped while offline, since reads come from the server.

## Generation with a subscription (no API cost)

By default the server's worker generates observations with a metered
`ANTHROPIC_API_KEY`. You can instead use a **Claude subscription**, so generation
costs nothing per token.

```bash
# 1. On the host, mint a long-lived OAuth token (interactive login, ~1 year):
claude setup-token            # prints sk-ant-oat01-...

# 2. Point the worker at subscription mode + the token (use a .env or secret file):
echo 'CLAUDE_MEM_SERVER_PROVIDER=subscription' >> .env
echo 'CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat01-...' >> .env

# 3. Restart the stack:
sudo systemctl restart claude-mem      # or: docker compose up -d

# 4. Confirm the worker is generating (and no longer restart-looping):
docker compose -p claude-mem logs -f claude-mem-worker
```

<Note>
The token lasts about a year — re-run `claude setup-token` and update the env when
it expires. If you see `auth_invalid` errors in the worker logs, the token has
expired or is wrong.
</Note>

## Generation with a local open-source model (Ollama)

The worker can generate against **any OpenAI-compatible endpoint** via the
`openrouter` provider, including a **local model** served by Ollama, vLLM, or
LM Studio. A local model means generation is free, private, and works offline —
your memory never leaves the machine.

This walks through Ollama on the same host as the server stack.

```bash
# 1. Install Ollama and bind it so the worker container can reach it (0.0.0.0):
curl -fsSL https://ollama.com/install.sh | sh
sudo mkdir -p /etc/systemd/system/ollama.service.d
printf '[Service]\nEnvironment="OLLAMA_HOST=0.0.0.0:11434"\n' \
  | sudo tee /etc/systemd/system/ollama.service.d/override.conf
sudo systemctl daemon-reload && sudo systemctl restart ollama

# 2. Pull a model with strong structured-output (XML) adherence:
ollama pull qwen2.5:7b-instruct
```

Let the worker reach the host's Ollama. In `docker-compose.my.yml`, add to the
`claude-mem-worker` service:

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

If the host firewall denies incoming connections (e.g. `ufw`), allow the Docker
subnet to reach Ollama — this is the most common reason the worker can't connect:

```bash
sudo ufw allow from 172.16.0.0/12 to any port 11434 proto tcp comment 'docker -> host ollama'
sudo ufw reload
```

Point the worker at the local model (in `.env`):

```bash
CLAUDE_MEM_SERVER_PROVIDER=openrouter
CLAUDE_MEM_OPENROUTER_BASE_URL=http://host.docker.internal:11434/v1
CLAUDE_MEM_SERVER_MODEL=qwen2.5:7b-instruct
OPENROUTER_API_KEY=ollama   # dummy; the provider requires a non-empty value
```

Then restart and confirm the worker reaches Ollama and produces observations:

```bash
sudo systemctl restart claude-mem      # or: docker compose up -d
docker exec <worker> curl -s http://host.docker.internal:11434/api/version
docker compose -p claude-mem logs -f claude-mem-worker
```

<Note>
**Model choice matters.** Generation must emit a specific observation XML format,
so use a capable instruction-follower. `qwen2.5:7b-instruct` (~5 GB VRAM) works
well and runs fully on an 8 GB GPU; step up to `qwen2.5:14b` or `32b` for better
adherence (at the cost of speed / partial CPU offload). Small 7B-and-under models
from weaker families may emit malformed XML and fail jobs. Switch models by
changing only `CLAUDE_MEM_SERVER_MODEL`.
</Note>

## Notes & limits

- **One trusted network.** These modes assume a single owner on a trusted tailnet. The
  server uses API-key auth; keep it off the public internet.
- **No provider key on clients.** Generation is the server's job — only the server's worker
  needs `ANTHROPIC_API_KEY` (or another provider). Without it the server still ingests
  events but won't produce summaries.
- **Switching modes** is done by re-installing with a different `--mode`.
- **Revoking a device** — revoke its API key on the server (`server api-key revoke`) and the
  client can no longer write.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `client status` shows `reachable: false` | Server up? URL is the tailnet address, not `localhost`? Firewall/Tailscale ACL allows the port? |
| `spoolDepth` keeps rising | Server unreachable or key revoked. Fix connectivity; the spool flushes automatically. |
| No memory injected at session start | Server has observations for this repo? Generation needs a provider key on the worker. |
| Remote device can't reach an enrolled server | The enrollment `--url` must be reachable from that device (tailnet IP, not `127.0.0.1`). Re-enroll with the correct URL. |
